1 · The problem, and what "totally different approach" meant

before

Routed scans died instantly

A routed scan crashed the moment the route emitted its first message, and the crash reason existed only in a live SSE stream that vanished on refresh. If nothing went wrong, an empty result looked identical to a failed one.

after

Failures are first-class; results are durable

The route emits through a typed adapter, failures persist an error column and show a red banner, empty-but-successful scans get an amber notice, and every port card, triage label and export is re-rendered from SQLite.

Same UI, same routes — but the state now has one owner (the database) and the engine reports what really happened instead of silently returning an empty result.

2 · Four egress routes, one policy object

The route is chosen per scan. Tor is the default, so forgetting to pick a route never scans from the operator's real IP. A route is validated before the scan starts and the engine refuses rather than silently falling back to a different egress path.

3 · The scan lifecycle

Every step writes durable state, so the UI can reconstruct the whole story even after a refresh.

  1. Authorize. Authorization is logged before any scanning; the engine refuses to run without a matching record.
  2. Preflight. Resolve the nmap binary, check privileges, and degrade the profile honestly when raw sockets aren't available.
  3. Plan the route. build_route_plan() validates tools and returns a RoutePlan — or an error that refuses the scan.
  4. Rewrite flags. A SOCKS route forces a TCP connect scan and drops flags it cannot carry.
  5. Activate. Start tor.exe or wait for the VPN tunnel; report failure in the returned state.
  6. Run & stream. nmap output is classified (port / phase / stats / warn) and pushed to the SSE stream.
  7. Parse & verify. The XML is parsed for hosts, ports, OS matches — and nmap's own runstats error, which now fails the scan loudly.
  8. Correlate. Ports are matched against ExploitDB + NVD, through the same proxy, to avoid leaking the real IP.
  9. Persist & render. Results land in SQLite; the page renders from the DB, not from memory.
  10. Tear down. The Tor daemon started for this scan is stopped again.

4 · Five defects, ranked by blast radius

#DefectSymptomFix
1critical Event signature mismatch Every routed scan crashed with emit() missing 1 required positional argument — the route emits dicts, emit wanted (kind, message). A _route_event adapter maps dict → typed emit.
2high Silent nmap errors nmap writes fatal flag errors into the XML with exit="error" while exiting 0, so a failed scan was recorded as completed, 0 ports. The parser exposes meta.error and the engine raises instead of reporting an empty success.
3high Failures were invisible The crash reason lived only in the live stream; after a refresh the scan looked like a quiet zero-result. An error column persisted on the scan and a red banner in the UI.
4medium Shadowed dropped list route_dropped_flags was always empty, hiding which flags a SOCKS route disabled. The list is initialised once and populated before use.
5low create_scan dropped error Seeding a scan with an error silently lost it (only update_scan persisted it). The INSERT now includes the error column.

5 · The structure after the pass

Two concerns were previously entangled: deciding the egress and running the scan. They now live in different modules with a single direction of data flow.

Egress policy

app/network.py

Owns: route catalog, tool detection, the RoutePlan, flag rewriting, daemon start/stop. Never runs nmap.

Orchestration

app/scan/engine.py

Owns: preflight, the run loop, streaming, teardown. Delegates routing to network.

Data shape

app/scan/parser.py

Owns: nmap XML → models, including runstats exit/error. No process logic.

Persistence

app/db.py

Owns: scans, ports, candidates, audit. The single source of truth the UI renders from.

Interface

app/main.py

Owns: HTTP routes, the worker thread, SSE, and render-ready view models.

State ownership: the plan is an input, not a scratchpad

before

ensure_route() set plan.ok = False on runtime failure, so the same object was both the validated request and the runtime outcome. Callers had to re-read a mutated plan to learn what happened.

→
after

ensure_route() returns {ok, error, tor_proc, …} and never touches the plan. The engine reads the state; the plan stays the immutable thing it was validated as.

Also removed: a dead duplicate platform_name() in the engine, unused platform/sys imports, and a doubled shutil.which scan in detect_programs(). The _prepare_route() extraction keeps run() about executing a scan, not about choosing an egress path.

6 · What Tor can and cannot do here — the honest limits

These are protocol realities, not bugs. The engine surfaces them in the scan log so an operator is never misled.

LimitWhyConsequence
TCP connect scan forcedA SOCKS proxy cannot carry raw SYN packets, so -sS, -O and fragmentation are dropped and -sT is inserted. Slower scans; OS detection is unavailable through the route.
tcpwrapped resultsTor exits may accept the connection and close it without a banner. A port reported tcpwrapped is expected, not a misconfiguration.
DNS is not resolved by the proxynmap's --proxies speaks SOCKS4, which has no remote hostname resolution. Scan IP addresses: a hostname is resolved locally first (a DNS leak).
Proton VPN needs the appThe official Windows client has no CLI; the installer can only point you to the download page. The route waits for the tunnel interface (up to 120s) and refuses rather than scanning the wrong egress.
Throughput through Tor is inherently slow and jittery. A single small scan of scanme.nmap.org took 68s — mostly Tor circuit latency, not the tooling.
